# 架构说明

## 目标

首版优先验证“问答有可靠来源”和“三类人生信息可持续维护”，避免在产品尚未验证时拆分微服务。后端采用模块化单体：一个部署单元，内部保持清晰边界，未来可按实际负载拆分。

## 目录边界

```text
apps/
  api/          NestJS API、定时任务、Prisma 数据模型
  miniprogram/  Taro + React 微信小程序
  admin/        Vite + React 内容管理端
packages/
  contracts/    跨端数据契约与校验规则
docs/
  architecture/ 架构与 ADR
  product/      产品边界
  security/     数据与隐私规则
```

业务模块不得直接读取其他模块的内部文件；共享输入输出放入 `packages/contracts`。数据库结构只能通过 Prisma migration（迁移，即可追踪的数据库变更脚本）演进。重要架构变更先新增 ADR，不将任何活跃文件永久冻结。

## 请求链路

1. 小程序用 `wx.login` 获取临时 code，后端调用微信 `code2Session` 并签发自己的短期 JWT。
2. 所有用户数据查询必须包含当前 `userId`，更新和删除前再次验证归属。
3. 问答服务先分类，再检索已核验资料，最后把资料作为受限上下文交给模型。
4. 外部链接只保存元数据和原始 URL；受限平台在小程序中采用复制链接，不绕过平台限制。
5. 文件由后端签发五分钟有效的上传地址；下载地址必须先验证文件归属。

## 运行依赖

- PostgreSQL：业务数据和外部内容元数据；
- Redis：为后续缓存、分布式限流和任务队列预留，首版定时提醒由单实例调度；
- S3/MinIO：简历和联系人照片；
- OpenAI 兼容接口：可选；默认 mock provider 允许无密钥开发和测试。

## 演进条件

只有在独立扩缩容、故障隔离或团队所有权出现明确需求时才拆服务。拆分前必须建立事务边界、幂等消息和可观测性，不能仅按功能名称拆分。
